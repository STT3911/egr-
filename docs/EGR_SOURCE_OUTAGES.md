# Временная недоступность дневных выгрузок ЕГР

Для `get*ByPeriod` ожидание чтения увеличено с 30 до 120 секунд. Для карточек
компаний остаётся прежнее ожидание 30 секунд. Три ограниченные транспортные
попытки сохранены; некорректный JSON и ошибки схемы не превращаются в пустые данные.

В `egr_period_sync_v2` добавлены необязательные поля, миграция БД не требуется:

- `collecting`: уже проверенные части восьми дневных источников. После сбоя
  повтор начинает с недостающего источника, не перезапрашивая успешные части.
- `source_retry`: тип временной ошибки, день, источник и срок следующей попытки.
  Пауза растёт 1 → 2 → 4 часа. Более длинный корректный `Retry-After` соблюдается.

Таймауты, сетевые разрывы, HTTP 429 и 5xx возвращают `source_unavailable`, сохраняя
день/УНП незавершённым. В течение паузы возвращается `cooldown` без обращений
к ЕГР. Первый сбой отправляет предупреждение, повторные сбои того же эпизода
не дублируют его в Telegram. После успешного возобновления отметка сбоя удаляется.

Ошибки авторизации, схемы данных, сохранения в БД и согласования истории не
подавляются. Контрольная дата синхронизации не продвигается через незавершённый
день. Все восемь источников по-прежнему должны быть проверены перед обработкой
компаний и подтверждением дня. Пауза не отменяет мониторинг отставания.

Исправление не может восстановить недоступный внешний API. Если запрос даже
за 120 секунд не отвечает, отставание остаётся видимым; сбрасывать checkpoint
или пропускать дату ради зелёного статуса нельзя.

Проверки: `tests/test_egr_source_outage.py`, `tests/test_egr_period_sync.py`.
Выкладка требует штатного перезапуска тяжёлого worker после окончания его
активной задачи. API, БД, Bankrot и суды перезапускать не требуется.

## Неполные переходы ИП → юрлицо

`getIPtoJurByPeriod` может вернуть запись без `ipngrn`. Если хотя бы один УНП
корректен, запись сохраняется целиком в `transition_conflicts` той же контрольной
точки. Отсутствующие, пустые, нулевые и некорректные идентификаторы не угадываются
и не попадают в `egr_ip_to_jur`. Строка без единого корректного УНП, неизвестная
структура ответа или подозрение на усечение по-прежнему останавливают сбор.

Известный УНП входит в обычную обработку карточек. Полные связи записываются как
раньше. Неполные связи не блокируют оставшиеся компании и последующие дни:
`scanned_through` показывает обработанные дни, а `last_completed_day` и старый
мониторинговый курсор не продвигаются через неразрешённый пробел. Наличие очереди
означает `blocked`, а не полностью успешную синхронизацию. Планировщик продолжает
новые окна даже при незакрытой очереди; ручной `sync_egr_window.py` завершает
такое окно с ненулевым кодом, не выдавая частичный результат за полный.

Очередь переживает перезапуск, повторный импорт не создаёт дубликаты наблюдений.
Через час повторно запрашивается только нужный дневной источник, затем интервал
растёт до суток. Не более трёх дней перепроверяются за запуск; большая часть
лимита карточек остаётся для новых данных. Ошибка сети при сверке откладывает
именно сверку, не весь новый день. Исходные наблюдения не удаляются при пустом
или изменившемся ответе.

Автоматическое разрешение допустимо только при единственной полной записи
того же дня, совпадающей со всеми исходными полями, кроме некорректного УНП.
Совпадение только имени не используется. Оба УНП проходят обновление карточек;
сохранение связи и подтверждение очереди выполняются одной транзакцией.
После разрешения исходное неполное наблюдение остаётся в
`transition_resolutions` вместе с полным ответом; аудит переносится в новые окна.
Неоднозначность остаётся для ручной сверки. Контрольная точка и номер миграции
совместимы с предыдущими данными; новая миграция не нужна.

Админский статус дополнен `sync_unresolved_transitions` и `sync_scanned_through`.
Telegram сообщает о новом составе очереди и её разрешении, без исходных ФИО
и без повторения одного конфликта каждый час. Алерты отставания полной
синхронизации при этом не отключаются.

Дополнительные проверки: `tests/test_egr_transition_reconciliation.py`.

## Мониторинг обработки и полноты: 19.10.2026

В Grafana `egr-sources` старый индикатор смешивал отставание обработки со сроком
полной сверки: одна неполная связь удерживала дату 12 октября и давала красную
«неделю», хотя все дни по 18 октября были обработаны.

Теперь показаны отдельно:

- Отставание обработки: число пропущенных дней относительно вчерашнего дня
  по `Europe/Minsk`, приоритет `scanned_through`, затем совместимый fallback
  `last_completed_day` / `egr_last_sync_date`. Отсутствие даты — «Нет данных»,
  а не зелёный ноль. Единица `none` сохраняет число дней без пересчёта в недели.
- «Данные обработаны по» и «Полностью сверено по» — две разные даты.
- Неполные связи и конфликты истории — отдельные жёлтые предупреждения при
  ненулевой очереди. Очереди, исходные ответы и контрольные даты не изменяются.

Сводный алерт `tendex_health_summary` проверяет настоящее отставание по дате
обработки; отсутствие даты или более трёх пропущенных дней остаётся критическим
сбоем. Неполные связи/истории создают отдельные предупреждения с обеими датами.
Разрыв между датами без сохранённой очереди тоже не маскируется. Правила прочих
источников, ошибок SQL и raw-backlog сохранены.
