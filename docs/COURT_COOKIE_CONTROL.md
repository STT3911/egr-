# Обновление court.cookie через Telegram

## Что подготовлено

`scripts/court_cookie_bot.py` — отдельный контроллер на Linux-хосте, без БД,
Celery и зависимостей Python. Он наблюдает только за `egr_court_export`:

1. При **подтверждённом отказе авторизации** отправляет запрос куки в заданный
   `COURT_CONTROL_CHAT_ID`. Требуются и exit code 2, и известное сообщение об отказе
   авторизации текущего запуска. Ошибки аргументов CLI с exit code 2 не считаются
   истечением куки.
2. Принимает полный Cookie текстом, `/cookie ...` или UTF-8-файлом `.txt`
   (до 16 КБ) **только в личном чате от `COURT_CONTROL_USER_ID`**.
   Обычное сообщение `ASP.NET_SessionId=...; .ASPXAUTH=...` принимается без команды.
   Приветствия `/start` и `/help` не повторяются чаще раза в 5 минут, даже после
   перезапуска службы. Уведомление об остановке в том же личном чате уже считается
   приглашением отправить куку. Ограничение приветствий не мешает приёму куки.
3. Требует `ASP.NET_SessionId` и `.ASPXAUTH`. Формат не доказывает действительность сессии.
4. Если контейнер остановлен, атомарно заменяет `court.cookie` с правами 0600
   и запускает тот же контейнер по его ID. Не меняет JSONL, checkpoints,
   даты, типы процессов, интервалы и файл ограничения частоты запросов.
5. Пытается удалить входящее сообщение с секретом; при неудаче просит удалить вручную.

Пока выгрузка работает/останавливается, кука **не заменяется**: текущий клиент
может перезаписать её из своей старой сессии. Не запускайте контейнер вручную
одновременно с отправкой новой куки. Контроллер не запускает контейнеры из
сообщений, не принимает shell-команды, не создаёт новый экспортёр.

Текущий экспортёр ограничен экономическими судами и параметрами своего контейнера.
Это не импорт в PostgreSQL, не привязка по УНП и не загрузка всех документов.
Контроллер не расширяет эти границы.

## Безопасность и ограничения

- Куки дают доступ к аккаунту. Личный чат с ботом не является секретным E2E-чатом.
  Передавать секрет через Telegram — осознанный компромисс; SSH остаётся альтернативой.
- Нельзя принимать куки в группе, от пересланных сообщений или по одному username.
  Нужен точный числовой user_id. Уведомления могут идти в другой, групповой chat_id.
- Пользователь должен сначала открыть бота и отправить `/start`.
- Используйте отдельного бота либо существующего Alerts-бота **без другого getUpdates
  потребителя/webhook**. Проверка webhook ничего не удаляет; конфликт 409 завершает
  контроллер. Не запускайте второй poller для поискового бота.
- Никаких значений куки/токена в логах, Telegram-ответах, аргументах Docker или state.
- State и cookie находятся вне Git; 0600, владелец пользователь службы. Каталог не
  должен быть доступен для записи другим пользователям. Контроллер имеет доступ
  к Docker от имени host-user; это привилегированный доступ, не песочница.
- Update ID записывается до побочных действий: повторная доставка не запускает
  экспортёр дважды. При аварии между сохранением ID и запуском потребуется **заново
  прислать** куку. Автоматических циклов запуска при невалидной куке нет.
- Сообщения старше 10 минут не применяются. При долгом простое пришлите свежую куку
  повторно. State-файл не удалять для «сброса»: он защищает от повторной обработки.
- Уведомление об остановке не означает, что причиной точно является кука. HTTP 200
  с пустым телом повторяется на той же странице максимум три раза через обычный
  интервал запросов. После трёх пустых ответов экспортёр останавливается и сохраняет
  `blank_response`, HTTP-статус и размер ответа в безопасном логе. Контроллер
  автоматически возобновляет тот же контейнер после паузы 10, 20, 40, максимум
  60 минут при повторных сбоях на том же месте. Новый прогресс сбрасывает паузу
  до 10 минут. Deadline и счётчик сохраняются при перезапуске контроллера.
  Страница остаётся незавершённой, cookie не меняется. Ошибка пустого ответа
  отправляется в обычный чат Tendex Alerts; в чат обновления куки она не идёт.
  Нераспознанная разметка (`unrecognized_response`) и неожиданный redirect
  (`unexpected_redirect`) останавливают выгрузку сразу. Ошибка авторизации
  обрабатывается отдельно и не запускает эти повторы.
- Экспортёр с `--notify-telegram` разделяет два назначения: подтверждённые ошибки
  авторизации идут в `COURT_CONTROL_CHAT_ID`, остальные ошибки — в обычный
  `ALERT_TELEGRAM_CHAT_ID`. При свежем `.court-control-heartbeat.json` (менее
  120 секунд) auth-уведомление отправляет только контроллер, чтобы не было дублей.
  Если контроллер не работает, экспортёр отправляет резервный auth-alert в чат
  из heartbeat (`auth_chat_id`); timestamp и числовой ID не содержат секретов.
  Для запуска без контроллера отдельный auth-чат можно явно задать через
  `COURT_AUTH_TELEGRAM_CHAT_ID`; без отдельной настройки сохраняется старое
  поведение standalone-экспортёра — auth-alert в обычный чат.
  Дедупликация контроллера — по FinishedAt контейнера. Обычные ошибки сохранения,
  изменённая разметка и redirect отправляются в обычный чат и сохраняются в логах,
  но не вызывают запроса куки. Контроллер не дублирует доставленные обычные ошибки
  экспортёра: он проверяет отметку `Court Telegram notification: sent` текущего
  запуска. Для уже запущенного старого экспортёра или недоставленного сообщения
  контроллер отправляет обычную ошибку в `COURT_CONTROL_DEFAULT_ALERT_CHAT_ID`.
  Команда `/status` в личном чате показывает работу, срок повтора
  пустого ответа или ожидание новой куки после ошибки авторизации.
- После остановки без подтверждённой ошибки авторизации и без запланированного
  возобновления контроллер проверяет доступ к странице решений одним GET-запросом
  не чаще раза в час. Общий интервал запросов не менее 30 секунд сохраняется.
  Проверка не следует редиректам, не повторяет HTTP, не изменяет cookie или
  JSONL/checkpoint. Только login-редирект/форма входа, REQUIRES_AUTH=1 или 401/403
  вызывают запрос куки в отдельный чат. Пустой 200, сеть, 5xx и неизвестный
  redirect не считаются истечением куки. Результат отбрасывается, если за время
  запроса изменились cookie, запуск или состояние контейнера. Уже обработанные
  старые остановки также проверяются; успешная отправка и Telegram message_id
  сохраняются в state без секретов, поэтому запрос куки не дублируется.
  Для диагностики старого файла допускается кука только сессии: отсутствие
  `.ASPXAUTH` не блокирует запрос к сайту, но само по себе не считается
  подтверждённым отказом авторизации. Новые куки из Telegram по-прежнему
  принимаются только с обеими обязательными парами.

## Настройка (после согласования бота и ID)

Файл `/home/user/egr-secrets/court-control.env`, права 0600, вне репозитория:

```ini
COURT_CONTROL_BOT_TOKEN=<секрет выбранного бота, заполнить только на сервере>
COURT_CONTROL_USER_ID=<числовой user_id разрешённого человека>
COURT_CONTROL_CHAT_ID=<числовой chat_id для уведомлений>
COURT_CONTROL_DEFAULT_ALERT_CHAT_ID=<обычный чат Tendex Alerts, отличный от чата куки>
COURT_CONTROL_COOKIE=/home/user/egr-secrets/court.cookie
COURT_CONTROL_STATE=/home/user/egr-secrets/court-control-state.json
```

Значения токена не передавать через чат или командную строку. Для существующего
Alerts-бота перенести секрет локально на сервере, не распечатывая его.

Шаблон службы: `deploy/court/court-cookie-bot.service` (User=user,
`/home/user/egr-dev/scripts/court_cookie_bot.py`). Python >= 3.10, Docker CLI
`/usr/bin/docker`; контейнер должен существовать и иметь bind mount родительского
каталога cookie на `/court-secrets`. Другие Docker-сервисы контроллер не меняет.

После проверки путей, прав, выбранного бота и разрешённых ID:

```bash
sudo install -m 0644 /home/user/egr-dev/deploy/court/court-cookie-bot.service /etc/systemd/system/court-cookie-bot.service
sudo systemctl daemon-reload
sudo systemctl enable --now court-cookie-bot
sudo systemctl status court-cookie-bot --no-pager
sudo journalctl -u court-cookie-bot -n 30 --no-pager
```

Без конфигурации служба не включается автоматически самим патчем.

### Служба пользователя без sudo

Альтернативный шаблон — `deploy/court/court-cookie-bot.user.service`. Для него
используются `systemctl --user` и включённый linger, чтобы работа не зависела
от открытого SSH. Не включать одновременно системную и пользовательскую службы.
На server1 выбран именно этот вариант:

```bash
loginctl enable-linger user
install -d -m 0700 /home/user/.config/systemd/user
install -m 0644 /home/user/egr-dev/deploy/court/court-cookie-bot.user.service /home/user/.config/systemd/user/court-cookie-bot.service
systemctl --user daemon-reload
systemctl --user enable --now court-cookie-bot.service
systemctl --user status court-cookie-bot.service --no-pager
journalctl --user -u court-cookie-bot.service -n 30 --no-pager
```

`scripts/setup_court_cookie_bot.py --user-id <ID> --chat-id <ID>` может создать
новую конфигурацию из существующего Alerts-токена внутри `egr_api`, не выводя
его наружу. Он отказывается перезаписывать существующий env, проверяет личный
чат, отсутствие webhook, отдельность поискового бота и bind mount экспортёра.
Сам по себе этот шаг не запускает экспортёр и не читает содержимое cookie.

Перед передачей реальной куки проверить `/start` с разрешённой учётной записи;
чужая учётная запись/группа не должны давать ответа или запускать Docker.
После обновления проверить только безопасные метаданные:

```bash
docker inspect --format 'status={{.State.Status}} exit={{.State.ExitCode}}' egr_court_export
docker logs --since 10m --tail 30 egr_court_export
stat -c '%a %U %n' /home/user/egr-secrets/court.cookie
```

Не печатать содержимое cookie, env, полный Docker inspect или Telegram updates.

## Проверки

`tests/test_court_cookie_bot.py`: авторизация, группы/forward, дубли updates,
ошибки записи и запуска, уведомления, удаление сообщения, ограничения файла,
совпадение bind mount, отсутствие секрета в ответах и исключениях.
Это синтетические проверки, не подтверждение доставки в реальный чат.

Telegram API: https://core.telegram.org/bots/api#getupdates,
https://core.telegram.org/bots/api#deletemessage.
