
Система работает в несколько этапов.

Сначала она получает данные из внешнего источника. Потом, как правило, сохраняет их в "сыром" виде, чтобы не потерять исходный ответ и иметь возможность повторно обработать его без нового запроса во внешний сервис. После этого данные разбираются и раскладываются по нормальным рабочим таблицам. Отдельно обновляются справочники, а состояние всей цепочки контролируется через Docker, healthcheck, логи и служебные скрипты.

Основные компоненты такие:

- `PostgreSQL` — основная база данных;
- `Redis` — брокер и backend для Celery;
- `FastAPI` (`egr-api`) — API и точка входа;
- `Celery Worker` — фоновые задачи;
- `Celery Beat` — расписание;
- `Nginx` и frontend — внешний доступ и интерфейс.

## Откуда берутся данные

### 1. EGR Legacy API

Это основной источник данных по компаниям.

- URL: `https://egr.gov.by/api/v2/egr`

Из него система получает:

- базовую информацию по компании;
- историю адресов;
- историю наименований;
- историю ВЭД;
- данные по изменениям за период;
- события за период.

Если говорить совсем просто, именно этот источник даёт основной объём данных для EGR-части системы.

### 2. EGR Mobile API

Это дополнительный источник, который используется точечно.

- URL: `https://egr.gov.by/egrmobile/api/v1`

Из него мы берём:

- `commonInfo` — базовую карточку компании;
- `placeLocation` — текстовый адрес местонахождения.

На практике он используется как fallback для карточки компании и как отдельный источник для `placeLocation`.

### 3. GRP API

Это источник данных по налогоплательщику.

- URL: `http://grp.nalog.gov.by/api/grp-public/data`

Из него приходят:

- полное и краткое наименование;
- дата регистрации;
- код и название инспекции;
- статус;
- адрес.

### 4. Портал налоговой задолженности

Отдельный поток в системе связан с задолженностью.

- URL: `https://www.portal.nalog.gov.by`

Там работа идёт не через обычный REST, а через GWT-RPC. Для этого направления данные сначала собираются в JSON, а уже потом при необходимости импортируются в базу.

### 5. GIAS Directory API

Из GIAS используются реестры каталога:

- `https://gias.by/directory/api/v1/accredited_customers/page`
- `https://gias.by/directory/api/v1/locked_suppliers/page`

Оба источника читаются постранично через параметры `q`, `page`, `size`.

Для них в базе поддерживаются:

- текущее состояние реестров;
- журнал запусков синхронизации;
- история изменений по записям.
- привязка к основной таблице `egr_companies` по `УНП`.

### 6. Локальные JSON-файлы

Кроме внешних API, система использует и локальные JSON-файлы как промежуточный слой.

Основные папки:

- `data/egr_json_full`
- `data/grp_json`
- папка из `NALOG_DEBT_OUT_DIR` для задолженности

Они нужны не сами по себе, а как:

- резервная копия выгрузки;
- промежуточный формат пакетной загрузки;
- возможность повторного импорта без повторных обращений во внешний сервис.

## Куда данные сохраняются

### EGR: сначала в raw, потом в рабочие таблицы

Первый этап для EGR — это сохранение "сырых" данных в таблицу:

- `egr_raw_company_data`

В ней хранится:

- полный JSON-ответ в поле `data`;
- отдельно разложенные части:
  - `base_info`
  - `addresses`
  - `ved`
  - `names`
- служебные поля:
  - `processed_at`
  - `updated_at`
  - `last_error`

Это буферная таблица. Она нужна, чтобы разделить загрузку и разбор данных. Если что-то упало на этапе обработки, исходный ответ уже лежит в базе, и его можно обработать повторно.

После разбора данные расходятся по рабочим таблицам:

- `egr_companies`
- `egr_company_names_history`
- `egr_company_addresses_history`
- `egr_company_ved_history`
- `egr_company_contacts_history`

Отдельно адрес местонахождения из Mobile API сохраняется в:

- `egr_company_place_locations`

Там хранится и сырой ответ, и уже извлечённый человекочитаемый адрес.

### EGR: справочники

Справочники в системе не тянутся отдельным внешним вызовом. Они извлекаются из уже накопленных raw-данных EGR.

Используются таблицы:

- `ref_statuses`
- `ref_creation_methods`
- `ref_entity_types`
- `ref_authorities`
- `ref_liquidation_methods`
- `ref_ved`
- `ref_countries`
- `ref_soato`
- `ref_foundations`
- `ref_events`
- `ref_street_types`
- `ref_room_types`
- `ref_room_categories`
- `ref_settlement_types`
- `ref_document_types`
- `ref_currencies`
- `ref_positions`
- `ref_opf`

Смысл этих таблиц стандартный: не дублировать справочные значения в каждой записи, а хранить их отдельно и использовать через внешние ключи.

### GRP: тоже в два слоя

Для GRP логика похожая.

Сначала данные сохраняются в raw-таблицу:

- `grp_raw_data`

Потом, после разбора, попадают в структурированную таблицу:

- `grp_taxpayer_data`

В `grp_raw_data` лежат:

- сырой JSON;
- `http_status`;
- `last_error`;
- признак, распарсена запись или нет.

В `grp_taxpayer_data` уже лежат нормальные рабочие поля:

- `unp`
- `full_name`
- `short_name`
- `registration_date`
- `inspectorate_code`
- `inspectorate_name`
- `status_code`
- `status_date`
- `address`

### Налоговая задолженность

После импорта JSON по задолженности данные попадают в:

- `nalog_debt_records`

Основные поля там такие:

- `debtor_unp`
- `imns_code`
- `imns_name`
- `debt_date`
- `repayment_date`
- `slice_date`

Практический сценарий загрузки:

1. Сначала обновить схему БД миграциями.
2. Затем собрать JSON из `portal.nalog.gov.by`.
3. Потом импортировать JSON в `nalog_debt_records`.

Пример команд:

```bash
docker compose exec -T egr-api alembic upgrade head
docker compose exec -T egr-api python scripts/run_nalog_debt.py --mode monthly --to-db
docker compose exec -T egr-api python -c "from app.core.database import SessionLocal; from app.database.models import NalogDebtRecord; db=SessionLocal(); print({'count': db.query(NalogDebtRecord).count()}); db.close()"
```

Если есть Excel со списком компаний и УНП, его можно сверить с БД и таблицей задолженности так:

```bash
docker compose exec -T egr-api python scripts/check_tax_debt_excel.py data/company_lists/companies.xlsx --json
```

Важно:

- файл `.xlsx` должен лежать внутри проекта или в смонтированном в контейнер каталоге;
- `GRP` и налоговая задолженность — это разные источники и разные таблицы;
- для `nalog_debt_records` уникальность должна быть по набору `debtor_unp + imns_code + debt_date + repayment_date + slice_date`.

## Короткая сводка: источник -> куда пишется

| Источник | Что получаем | Куда сохраняем |
|---|---|---|
| EGR Legacy API | base info, names, addresses, VED, изменения, события по периодам | сначала `egr_raw_company_data`, потом `egr_companies`, `egr_company_names_history`, `egr_company_addresses_history`, `egr_company_ved_history`, `egr_company_contacts_history` |
| EGR Mobile API | `commonInfo`, `placeLocation` | fallback в `egr_raw_company_data`, отдельно `egr_company_place_locations` |
| EGR raw-данные | справочные значения | таблицы `ref_*` |
| GRP API | сведения о налогоплательщике | сначала `grp_raw_data`, потом `grp_taxpayer_data` |
| portal.nalog.gov.by | задолженность | JSON, затем `nalog_debt_records` |
| GIAS Directory API | аккредитованные лица / временно недопущенные поставщики | `gias_accredited_customers`, `locked_suppliers`, таблицы истории и `gias_sync_runs` |
| EGR JSON | пакетная загрузка EGR | `egr_raw_company_data`, затем рабочие EGR-таблицы |
| GRP JSON | пакетная загрузка GRP | `grp_raw_data`, затем `grp_taxpayer_data` |

## Как часто данные загружаются

### EGR

Для EGR в Celery Beat настроен регулярный поток.

- `egr_fetch_raw` — каждые `60 секунд`
  - идёт во внешний EGR API;
  - обновляет `egr_raw_company_data`.

- `egr_process_raw` — каждые `20 секунд`
  - берёт накопленные raw-данные;
  - раскладывает их по рабочим EGR-таблицам.

- `load_companies_from_json` — каждый день в `02:00`
  - загружает EGR из локальных JSON.

- `sync_daily_changes` — каждый день в `03:00`
  - забирает изменения за предыдущий день;
  - ставит компании в очередь на обновление.

- `update_reference_tables` — каждый день в `04:00`
  - обновляет `ref_*` таблицы из EGR raw-данных.

- `egr_sync_place_locations` — каждые `10 минут`
  - подтягивает `placeLocation` из Mobile API.

- `reprocess_failed_rows` — по субботам в `05:00`

### GIAS Directory

Для GIAS в Celery Beat настроена ежедневная синхронизация.

- `sync_gias_directory_registries` — каждый день в `04:30`
  - обновляет `gias_accredited_customers`;
  - обновляет `locked_suppliers`;
  - пишет журнал в `gias_sync_runs`;
  - сохраняет историю изменений в `gias_accredited_customers_history` и `locked_suppliers_history`.
  - повторно пытается обработать записи, которые раньше завершились ошибкой.

- `auto_fetch_historical_data` — по воскресеньям в `01:00`
  - выполняет историческую догрузку большими периодами.

### GRP

По умолчанию GRP в расписании выключен.

Если включить:

- `GRP_SCHEDULE_ENABLED=true`

тогда запускаются:

- `grp_fetch_raw` — каждые `120 секунд`
- `grp_process_raw` — каждые `30 секунд`

То есть основной GRP-поток может работать автоматически, но только если его явно включить.

Практическая политика для GRP такая:

- Нормальное состояние:
  - `grp_raw_data` может быть больше, чем `grp_taxpayer_data`.
  - Разница между ними (`diff = raw - taxpayer`) сама по себе не означает сбой.
- Что означает `diff`:
  - `grp_raw_data` хранит и успешные ответы, и терминальные ошибки fetch.
  - `grp_taxpayer_data` заполняется только для записей, по которым есть валидный payload GRP.
  - Поэтому часть строк может существовать только в raw-слое и никогда не появиться в `grp_taxpayer_data`.
- Какие случаи считаются нормальными:
  - `429 Rate limit exceeded` — временная ошибка. Такие записи нужно повторять позже, а не считать потерянными.
  - `400 Bad Request` от GRP — терминальный случай для конкретного УНП. Такие записи можно считать обработанными, но не нужно искусственно создавать по ним пустые строки в `grp_taxpayer_data`.
- Как понимать здоровье очереди:
  - Основной сигнал — это `unparsed_raw`.
  - Если `unparsed_raw = 0`, очередь обработки пуста, даже если `diff > 0`.
  - Если `diff > 0`, но все такие записи имеют терминальные `400`, это не operational issue, а ожидаемое состояние данных.
- Какой режим считать правильным для production:
  - не перезапрашивать массово весь исторический GRP-срез;
  - хранить `80k+` уже полученных GRP-записей как рабочий снимок;
  - в фоне догонять только missing/retryable-хвост;
  - не затирать последний успешный `raw_json` при `429` и других временных сбоях.

### GRP через JSON

Отдельно у GRP есть JSON-сценарий:

- `fetch_grp_to_json(...)`
  - берёт УНП из базы;
  - ходит в GRP API;
  - сохраняет результат в `data/grp_json`.

- `load_grp_from_json(...)`
  - читает JSON-файлы;
  - грузит их в `grp_raw_data` и `grp_taxpayer_data`.

- `auto_fetch_grp_and_load(...)`
  - сначала собирает JSON;
  - потом сразу загружает его в базу.

На текущий момент это скорее пакетный или ручной режим, а не основной always-on поток.

### Задолженность

Поток по задолженности сейчас не стоит в обычном Celery-расписании.

Он запускается вручную через CLI-скрипты и при необходимости может быть вынесен в cron или Task Scheduler.

## Как мы понимаем, что сервисы работают нормально

### Docker healthcheck

Для ключевых компонентов в `docker-compose` уже настроены healthcheck:

- `db` — через `pg_isready`
- `redis` — через `redis-cli ping`
- `egr-api` — через запрос к `/api/v1/health`
- `frontend` — через локальный HTTP-запрос

За счёт этого Docker помечает контейнеры как:

- `healthy`
- `unhealthy`

И это уже даёт первый базовый уровень контроля.

### Порядок запуска

Сервисы не стартуют хаотично.

Например:

- `egr-init` ждёт, пока будут готовы `db` и `redis`;
- `egr-api` стартует после `db`, `redis` и завершения `egr-init`;
- `egr-celery-worker` и `egr-celery-beat` ждут готового API;
- `nginx` ждёт backend и frontend.

Это снижает риск ситуации, когда один сервис поднялся, а его зависимости ещё нет.

### Health endpoint API

У backend есть endpoint:

- `/api/v1/health`

Он показывает, что приложение отвечает.

Также есть:

- `/api/v1/health/ready`

Но тут есть важный нюанс: readiness пока упрощённый. Он ещё не делает полноценную проверку БД и других зависимостей.

### Логи

В реальной эксплуатации логи сейчас играют очень большую роль.

Смотрим в первую очередь:

- `egr-api`
- `egr-celery-worker`
- `egr-celery-beat`
- при необходимости `db` и `redis`

Если сервис начинает сбоить, это обычно видно либо по статусу контейнера, либо по логам, либо по тому, что перестают двигаться данные в таблицах.

### Диагностические скрипты

В проекте уже есть готовые скрипты для быстрой проверки:

- `scripts/status.sh`
  - показывает состояние контейнеров;
  - проверяет PostgreSQL, Redis, API, frontend, nginx и внешний доступ.

- `scripts/check-parsing-status.sh`
  - показывает, сколько raw-строк ещё ждут обработки;
  - сколько уже обработано;
  - сколько с ошибками;
  - в каком состоянии справочники;
  - живы ли Celery worker и beat.

- `scripts/check-data-status.py`
  - даёт сводную статистику по данным EGR.

## По каким признакам видно, что что-то пошло не так

### Если проблема с API

Обычно это заметно так:

- контейнер `egr_api` не `healthy`;
- `/api/v1/health` перестаёт отвечать;
- frontend или nginx не могут получить ответ от backend.

### Если проблема с Celery Worker

Типичные признаки:

- контейнер не запущен или `unhealthy`;
- в raw-таблицах копятся записи, а обработка не идёт дальше;
- `processed_at` или `parsed_at` перестают обновляться;
- в логах видно много `parse_failed`, `fetch_failed`, timeout или connection error.

### Если проблема с Celery Beat

Здесь основной симптом другой: задачи по расписанию просто перестают запускаться.

Это видно по тому, что:

- контейнер не работает;
- в логах нет плановых запусков;
- регулярные процессы перестают происходить в ожидаемое время.

### Если проблема с PostgreSQL

Обычно видно по следующим симптомам:

- `pg_isready` не проходит;
- API и worker не могут открыть сессию;
- в логах идут ошибки соединения или rollback;
- не отрабатывают миграции и init-скрипты.

### Если проблема с Redis

В таком случае обычно ломается очередь задач и кэш.

Признаки:

- `redis-cli ping` не отвечает;
- Celery не принимает или не выдаёт задачи;
- перестаёт работать кэширование профилей;
- beat и worker как будто есть, но фактического движения задач нет.

## Как это обычно проверяется на практике

На практике базовая проверка обычно выглядит так:

1. Проверить контейнеры:
   - `docker compose ps`

2. Проверить health основных сервисов:
   - PostgreSQL
   - Redis
   - API
   - frontend

3. Проверить, двигаются ли данные:
   - уменьшается ли `pending` в `egr_raw_company_data`
   - растёт ли `egr_companies`
   - уменьшается ли количество необработанных записей в `grp_raw_data`
   - растёт ли `grp_taxpayer_data`
   - для GRP отдельно смотреть:
     - `unparsed_raw` — это реальный хвост обработки;
     - `diff = grp_raw_data - grp_taxpayer_data` — это только справочный показатель, а не автоматический признак ошибки;
     - если `unparsed_raw = 0`, а `diff > 0` и хвост состоит из `400 Bad Request`, вмешательство не требуется.

4. Проверить логи:
   - `docker compose logs -f egr-api`
   - `docker compose logs -f egr-celery-worker`
   - `docker compose logs -f egr-celery-beat`

5. При необходимости запустить служебные скрипты:
   - `scripts/status.sh`
   - `scripts/check-parsing-status.sh`
   - `scripts/check-data-status.py`

## Что в текущей реализации ещё можно усилить

Система уже рабочая, но есть несколько мест, которые можно сделать сильнее.

- У `Celery worker` и `Celery beat` нет полноценного отдельного docker healthcheck.
  Сейчас их состояние оценивается в основном по логам, статусу контейнера и по косвенным признакам в таблицах.

- `/api/v1/health/ready` пока не делает реальную readiness-проверку подключения к БД.

- Для GRP есть отдельная ежемесячная задача экспорта `grp_monthly_export`, которая делает JSON-бэкап `grp_raw_data` и `grp_taxpayer_data` в папку экспорта.

- Таблица `egr_company_events` в модели есть, но в текущем регулярном pipeline не выглядит как полностью оформленный постоянный поток загрузки.

## Вывод

Если коротко, система забирает данные из нескольких источников:

- EGR Legacy API;
- EGR Mobile API;
- GRP API;
- портала налоговой задолженности;
- локальных JSON-файлов как промежуточного слоя.

Дальше данные проходят через понятную многоэтапную схему:

- raw-слой;
- структурированные таблицы;
- справочники;
- служебные поля и таблицы для контроля обработки.

Самый устойчивый и постоянно работающий поток сейчас реализован для EGR. Для GRP есть и прямой поток `API -> raw -> structured`, и JSON-сценарий `API -> JSON -> DB`.

Контроль работы сервисов строится на нескольких уровнях:

- Docker healthcheck;
- зависимости запуска между сервисами;
