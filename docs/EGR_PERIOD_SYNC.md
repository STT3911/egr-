# Ежедневные изменения ЕГР: все ByPeriod

Контракт сверён 18.09.2026 с `https://egr.gov.by/api/v2/api-docs`.
До этой доработки `sync_daily_changes` вызывала только BaseInfo и Event.
Наличие остальных методов в HTTP-клиенте не означало их вызов по расписанию.

| Метод | Что даёт | Ключи затронутых субъектов |
| --- | --- | --- |
| getBaseInfoByPeriod | Основные сведения | ngrn |
| getEventByPeriod | Регистрационные события | ngrn |
| getAddressByPeriod | Адреса | ngrn |
| getJurNamesByPeriod | Наименования юридических лиц | ngrn |
| getIPFIOByPeriod | ФИО ИП | ngrn |
| getVEDByPeriod | Виды деятельности | ngrn |
| getShortInfoByPeriod | Краткие сведения | ngrn |
| getIPtoJurByPeriod | Переход ИП в юридическое лицо | **ipngrn и ulngrn** |

## Алгоритм

1. За каждый день последовательно прочитать восемь лент. Объединить УНП,
   сохранить список, количества по источникам и события в `egr_system_state`.
2. Для каждого УНП строго загрузить основную карточку и полную историю адресов,
   наименований/ФИО, ВЭД и регистрационных событий. HTTP-ошибка, неверный JSON или неизвестный формат
   не подменяются пустым ответом. Для историй допустимы успешные пустые массивы.
3. Сохранить raw, сразу обработать карточку обычным агрегатором, поставить её
   в существующую очередь Elasticsearch и сбросить `company_profile_v2:{unp}`.
4. После успешной обработки записать события подписчикам и следующий индекс УНП
   одной транзакцией. Только после всех УНП завершить день.
5. При сбое продолжить с сохранённого индекса. Между коммитом карточки и коммитом
   прогресса возможен повтор одной карточки; обработка рассчитана на повторы.

Это не полная переборка реестра: загружаются только УНП из лент изменений.
Связь ИП→юрлицо сохраняется в `egr_ip_to_jur` и используется для обновления
обеих карточек. Индексация асинхронная, успешный sync не означает, что ES
уже успел обработать очередь.

## Продолжение и поздние публикации

- Основной запуск сохраняется в 03:00 (часовой пояс Celery).
- В :15 каждого часа та же задача проверяет незавершённую работу. Если окно
  за вчера уже завершено, HTTP-запросов не будет.
- Очередь `heavy`: быстрые задачи не блокируются синхронизацией. Нужен работающий
  worker этой очереди; её загруженность влияет на фактическое время запуска.
- PostgreSQL advisory transaction lock на отдельном соединении не допускает
  двух параллельных экземпляров новой задачи.
- Дата «вчера» вычисляется по Минску независимо от часового пояса контейнера.
- Каждый новый суточный цикл перепроверяет последние три дня. Публикации с
  большей задержкой требуют расширенного окна/отдельного backfill; гарантий
  отсутствия таких публикаций у источника нет.

Новый checkpoint — JSON под ключом `egr_period_sync_v2` в существующей таблице
`egr_system_state`. Он независим от старого `egr_last_sync_date`, поскольку
старый курсор не доказывает проверку остальных шести лент. Старый ключ остаётся
для совместимости мониторинга и не откатывается при повторной проверке истории.

Первый запуск новой версии проверит **последние 30 дней до вчера включительно**.
При запуске 18.09.2026 это 19.08–17.09, включая изменение адреса УНП 193879557.
Первоначальная обработка может занять несколько запусков. Более ранняя история
не считается проверенной этой доработкой.

Настройки (в env worker и при ручном запуске):

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| EGR_PERIOD_BOOTSTRAP_DAYS | 30 | Глубина **первого** запуска, до создания checkpoint |
| EGR_PERIOD_OVERLAP_DAYS | 3 | Повтор последних дней в новом суточном цикле |
| EGR_PERIOD_BATCH_SIZE | 500 | Максимум карточек за запуск |
| EGR_PERIOD_MAX_SECONDS | 1200 | Мягкий бюджет между запросами/карточками |
| EGR_PERIOD_REQUEST_DELAY | 0.5 | Пауза между запросами этой задачи, секунды |
| EGR_PERIOD_ROW_LIMIT | 2500 | Защита от возможного усечения суточной ленты |

Порог 2500 — консервативная защита из прежнего импортера, не документированная
гарантия Swagger. При достижении порога задача останавливается без продвижения
дня: нужно выяснить лимит/полноту ответа. Пагинация для этих восьми методов
в проверенном Swagger не описана. Не отключать защиту ради зелёного статуса.
Задача также останавливается на ошибке одной карточки; этот УНП остаётся pending.
Следующий плановый запуск повторяет его, не теряя остальных УНП.

## Адреса и история

Существующие строки истории теперь получают `valid_to` и исправленные поля,
а не пропускаются целиком. Это относится также к названиям и ВЭД. Старый raw
с пустым `valid_to` не может заново открыть уже закрытый период.

При подтверждённом новом текущем адресе из строгой загрузки сбрасываются только
производные `address/lat/lon/geocoded_at` кэша Mobile. Его `raw_json` и `fetched_at`
сохраняются. API с приоритетом Mobile сможет использовать свежий адрес истории.
Добавлены корпус и примечание адреса (включая комнаты). Однозначное уточнение
адреса того же периода не создаёт вторую строку истории.

Даты с часовым поясом переводятся в Минск. Старый ключ истории исправляется
только при однозначном совпадении с прежней UTC-датой из того же raw; массового
сдвига всех дат нет. При неоднозначности задача останавливается. Номера событий
хранятся как int64; повтор события обновляет существующую запись по ключу
компания/номер события, включая отмену события.

Ночной импорт всей папки старых JSON и еженедельный исторический обход теперь
выключены по умолчанию (`EGR_JSON_IMPORT_SCHEDULE_ENABLED=false`,
`EGR_HISTORICAL_SCHEDULE_ENABLED=false`). Ручные задачи остаются доступны.
Исторический экспорт пишет потоковый файл небольшими пакетами и продолжает
по дневному checkpoint. Перед запросами проверяются права записи и место.
Не включать старые снимки параллельно актуализации ByPeriod.

## Проверка перед production

Нужна миграция `egrapi2`: int64 номеров событий, уникальный индекс событий и
таблица связей ИП→юрлицо. Текущая цепочка от production:
`addrunit1 → court1schema → sourcefetch1 → egrapi2 → egrapi3`. Последняя миграция
добавляет created_at/updated_at событий, отсутствовавшие в исторической схеме.
Нельзя переносить только
последний файл миграции без его предшественников. Дубликаты событий намеренно
блокируют индекс, а не удаляются автоматически. См. `RELEASE_2026_09_21.md`.

1. Локальные тесты `test_egr_period_sync.py`, `test_egr_history_updates.py` и общий
   набор `tests`. HTTP замокан: тесты не доказывают работу production.
2. На dev проверить миграции PostgreSQL и API. В текущем dev Compose нет worker
   и beat; задачу проверять отдельным ручным запуском с dev-окружением. В production
   обновить также worker и beat, проверить очередь heavy. Не включать одновременно
   старую и новую версии worker.
3. Запустить `app.tasks.sync_tasks.sync_daily_changes`, проверить в логах все
   восемь счётчиков, прогресс `saved UNP` и итог `pending/complete`.
4. Проверить checkpoint read-only SQL:

   ```sql
   SELECT value::jsonb - 'pending' AS progress,
          value::jsonb #>> '{pending,day}' AS pending_day,
          value::jsonb #>> '{pending,next_index}' AS processed_in_day,
          jsonb_array_length(value::jsonb #> '{pending,unps}') AS total_in_day,
          value::jsonb #> '{pending,counts}' AS source_counts,
          updated_at
   FROM egr_system_state WHERE key = 'egr_period_sync_v2';
   ```

5. На УНП 193879557 проверить новую улицу Кнорина, дом 55, помещение 2-1,
   комнаты 13,14,15, закрытый старый адрес Макаенка и результат Bitrix-реквизитов.
   Затем проверить выполнение очереди Elasticsearch.
6. Только после dev-проверки переносить тот же проверенный набор в production.
   Не сбрасывать checkpoint и не удалять историю для повторного запуска.
