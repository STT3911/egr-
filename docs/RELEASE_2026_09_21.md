# Проверка релиза ЕГР и восстановления Bitrix

## Статус

Основной патч опубликован в develop и выложен пользователем на dev. Миграции
до egrapi2 применились, API healthy. Реальный импорт выявил отсутствие audit-полей
событий в исторической миграции: добавлена egrapi3 (нужна повторная dev-проверка).
Изменений CRM, миграций production и удаления серверных файлов не выполнялось.
После очистки пользователь сообщил о 35% свободного места; нехватка памяти
worker — отдельная проблема, она освобождением диска не устраняется.

## Состав и порядок

1. Сохранить production hotfix Bitrix из `e8f99bb`: прямые GET/POST обработчики
   `/bitrix/admin` и `/bitrix/install/`. Они восстановлены и проверены локально.
2. Надёжность источников: `source_fetch_state`, GRP/Mobile, лицензии, МНС, СЭЗ,
   task/config/model изменения, миграция `sourcefetch1` и соответствующие тесты.
3. ЕГР: восемь ByPeriod, строгая загрузка истории, mapper/CRUD/aggregator,
   `egr_contract`, `egr_period_sync`, `egr_snapshot`, миграция `egrapi2`, расписание
   и тесты. Эти части взаимозависимы — не выкладывать один HTTP-клиент отдельно.
4. Bitrix: client/requisite_service/keepalive, recovery и CLI, тесты.
   Восстановление CRM — отдельный ручной этап после проверки OAuth и preview.

Не включать автоматически постороннюю правку `nginx/conf.d/company.tenders.by.conf`
(Grafana burst) и `docs/COURT_JUDGMENTS.md`. В production уже есть локальная
правка Nginx — её сохранить. Не использовать `git add .`, `push --force` или
`push origin HEAD:main`: develop и main расходятся. Подготовить отдельную
release-ветку от актуального main, включить нужные изменения и миграционные
предшественники, затем повторить тесты именно на ней. Изменения судов не считать
автоматически проверенными для production только из-за зависимости миграций.

## Обязательные проверки перед production

- Свежая проверенная резервная копия БД вне контейнера; старые копии не удалять.
- Dev использует свою БД и не production OAuth/Telegram/подписки. Dev Compose
  содержит api/db/redis/frontend, но не worker/beat. Не поднимать второй production
  scheduler и не запускать импорт всей истории для smoke-test.
- На dev: собрать API, применить `alembic upgrade egrapi3`, проверить `alembic current`,
  наличие `source_fetch_attempts`, `egr_ip_to_jur`, тип bigint и уникальность событий.
- Проверить адрес УНП 193879557, закрытие старого адреса, повтор одной карточки без
  дублей, продолжение checkpoint после искусственной ошибки. Для источника нужны
  рабочий доступ и учёт ограничений; тесты с mock не заменяют эту проверку.
- До production миграции проверить дубликаты ненулевых номеров событий:

  ```sql
  SELECT company_id, event_record_id, count(*)
  FROM egr_company_events WHERE event_record_id IS NOT NULL
  GROUP BY company_id, event_record_id HAVING count(*) > 1;
  ```

- Цепочка: `addrunit1 → court1schema → sourcefetch1 → egrapi2 → egrapi3`.
  egrapi3 добавляет отсутствующие created_at/updated_at событий без удаления данных;
  старые неизвестные даты остаются NULL, новые получают default now().
  Изменение типа столбца/создание индекса требует окна обслуживания. Остановить
  beat и потребителей задач, дождаться завершения выполняемых работ; исключить
  записи API на время миграции. Затем обновить API, все соответствующие workers
  и beat одним проверенным релизом. Один `git pull` не обновляет уже импортированный
  Python-код работающего процесса.
- Контроль после старта: ready API, память/cgroup heavy, логи, pending ByPeriod,
  продвижение очереди Elasticsearch. Не повышать лимиты RAM вслепую.
- Откат: остановить новый scheduler/workers и вернуть предыдущий образ/код;
  не выполнять автоматический destructive downgrade. Удаление заполненных связей
  или сужение int64 отдельно запрещено защитой миграции.

## Ошибки 20–21 сентября

- Historical: на сервере были отказы записи JSON, SIGKILL и счётчики OOM heavy
  при лимите 384 MiB. Новый экспорт ограничивает параллелизм, пишет потоково,
  проверяет место/права до запросов, импортирует только свой завершённый файл.
  Еженедельный обход и ночной массовый импорт JSON выключены по умолчанию.
- ГИАС: сетевые timeout получают ограниченные отложенные повторы с сохранением
  курсора. Deadline повтора не наследует 110-секундный срок задачи beat.
  Это не гарантия доступности внешнего сайта.
- Bitrix: не смешивать истёкший access_token, недействительный refresh_token,
  неверные credentials приложения и HTTP403. Ошибка одного портала изолирована
  отдельной DB-сессией; refresh сериализован блокировкой строки.

## Восстановление autocrm

Нужны client_id/secret именно того приложения, которому принадлежат токены.
Предыдущая проверка выявила несоответствие приложения 210 сохранённым credentials;
перед восстановлением подтвердить актуальную установку. Не отправлять секреты
в чат/логи. При недействительном refresh_token администратор повторно авторизует
выбранную установку, после чего `app.info` должен соответствовать client_id.
Изменение кода само по себе не восстанавливает отозванные токены.

После выкладки запустить сначала preview (команда внутри API-контейнера,
каталог state должен быть постоянным и доступным для записи):

```bash
python /app/scripts/replay_bitrix_requisites.py \
  --domain autocrm.bitrix24.by \
  --since 2026-09-15T12:00:00+03:00 \
  --state-file /app/data/bitrix-recovery/autocrm-20260915.json \
  --limit 100
```

Повторять до `previewed == total`. Отбирается объединение созданных и изменённых
компаний; верхняя дата фиксируется первым запуском. Это выборка текущей CRM,
не исторический аудит удалённых компаний или перезаписанного DATE_MODIFY.

Применение — та же команда с `--apply --accept-portal-events`, сначала `--limit 5`.
После проверки результата продолжить с тем же state. Заполняются только пустые
реквизиты; ручные значения, имя компании, контакты и банковские счета не меняются.
Частично заполненный вручную адрес сохраняется целиком. При ошибке checkpoint
не перескакивает через компанию. Наш код не отправляет сообщения, однако события,
роботы и уведомления самого Bitrix могут сработать — проверить их до применения.
