# Проверка и догрузка отдельного периода ЕГР

`scripts/sync_egr_window.py` обрабатывает все восемь ByPeriod за указанные
завершённые дни по Минску, затем полную историю каждого найденного УНП.
Команда пишет бизнес-данные и события; это не dry-run.

Пример для production (Bash, `/home/user/egr`):

```bash
docker compose exec -T egr-api python -u /app/scripts/sync_egr_window.py \
  --date-from 2026-09-22 --date-to 2026-09-24 --database egr_db \
  --max-companies 500 --max-seconds 1200
```

Повторять ту же команду после `pending`. `complete` или `up_to_date` означает,
что это окно завершено; `already_running` — общую блокировку держит другой
запуск ЕГР, изменений этот вызов не сделал. Исключение сохраняет проблемный
УНП для повторной обработки, а не пропускает его.

Прогресс хранится в `egr_system_state` под ключом
`egr_period_window:2026-09-22:2026-09-24`. Общий ключ `egr_period_sync_v2` и
`egr_last_sync_date` не сдвигаются: отдельное свежее окно не должно скрывать
пробелы в старой догрузке. Используется та же advisory-блокировка, что у
ежедневной задачи; параллельных импортов через эти два пути не будет.

Исправление от 25 сентября сопоставляет точный старый формат адреса из
полей источника и единственные соответствия цепочек полных периодов.
Неотличимые дубли по-прежнему требуют разбора. Старые лишние наблюдения
не удаляются, произвольного выбора по порядку строк нет.

## Незавершённая основная синхронизация

`--backlog` использует существующий `egr_period_sync_v2`: `--date-from` его
не сбрасывает. `--max-batches` и `--total-seconds` разрешают последовательные
пакеты без ожидания очередного часового задания. Паузы между запросами
источника сохраняются; advisory-lock исключает параллельный импорт.

При конфликте истории снимок сохраняется, а УНП, день и события остаются в
`history_conflicts` контрольной точки. Другие компании продолжают
обрабатываться. `last_completed_day` не проходит через такой пробел,
`completed_target` не подтверждается. Следующий запуск повторяет до десяти
конфликтов (сначала наименее часто проверенные).

После обхода окна статус `blocked` / exit 3 означает незавершённые конфликты,
а не успех. Exit 4 означает исчерпание заданного бюджета, команду можно
повторить. Обычные ошибки сети, схемы источника и БД не превращаются в
конфликты истории и по-прежнему останавливают вызов с сохранением позиции.
